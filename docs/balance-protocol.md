# Balance-change protocol

The ordered procedure for changing any number the game plays by. Work through it top to bottom.
It is written as a list rather than as advice because a change that skips one of these steps
usually skips it silently, and nothing downstream notices.

**This applies to** any change to a formula, cost, price, rate, drop chance, encounter weight,
stat gain or region difficulty — in practice anything under `app/src/rules/`, and the numeric
constants in `app/src/game/`.

**It does not apply to** wording, presentation, layout, or a refactor that leaves every number
identical. Player-facing wording is an agent's own call and needs no escalation. One existing rule
still binds while you write it: a number the player *sees* comes from the game and not from a guess
(`CLAUDE.md:145-149`). Quoting a number is wording; *changing* it is a balance change, and lands
back here.

## The procedure

1. **State the design intent for the area you are touching**, in one sentence, quoting
   [design-vision.md](design-vision.md). If that document has no stated intent for the area, write
   one and add it in this same change — an area with no intent cannot be argued about, only
   preferred.

2. **Challenge the request.** Say what the change is trying to fix, and whether the game actually
   has that problem — measured, not felt. Then say what it costs: which of the intents in
   [design-vision.md](design-vision.md) it pushes against, and what a player loses. If the request
   conflicts with a stated intent, say so plainly and propose the alternative that does not, rather
   than implementing it quietly and leaving the conflict for someone to find later.

3. **Source every number.** Take each value from the table below. Never invent one. If the port
   lacks a value the change needs, record it in the harness and regenerate rather than guessing —
   that is the pattern the weapon pricing was ported with (`CLAUDE.md:145-149`).

4. **Assess the impact on progression and difficulty**, measured as campaign outcomes: win rate,
   death rate, Marks earned, level reached, per-region payoff. Never as run length or time to
   finish — the game is endless, so there is no run to be long (see
   [design-vision.md](design-vision.md)). The measures are the assertions in
   `app/test/balance.test.ts`, the `./gradlew baseline` diff, and the shape of
   `baseline/distributions.txt`. Test at three or more difficulty points — the starting region with
   a fresh character, a mid-level character, and a deep region — because a change that helps a
   veteran can make the first afternoon lethal. That is not hypothetical:
   `app/test/balance.test.ts:132-140` exists because it once happened.

5. **Keep every assertion in `app/test/balance.test.ts` true, or name the one you are deliberately
   breaking and why.** Those assertions are the design intent in executable form, so breaking one is
   a design change and has to be argued as one. If you do break it deliberately, update the
   assertion and its comment in the same change. A silently loosened assertion is the failure this
   step exists to prevent.

6. **Regenerate the baseline, then run the gate — in that order, never reversed.** The baseline
   artifacts are the tests' *input*, not their output: `app/test/parity.test.ts`,
   `app/test/economy.test.ts` and `app/test/balance.test.ts` all check against them, so a gate run
   against a stale baseline passes misleadingly. Only the ordering belongs to this document. The
   rule itself — regenerate, read the diff, say in the commit message what moved — is owned by
   `CLAUDE.md:150-155`, and the reasoning behind it by `docs/roadmap.md:14-35`.

7. **Update the design docs in the same commit.** [design-vision.md](design-vision.md) if the change
   moves stated intent; [gameplay.md](gameplay.md) if it moves a number that document quotes.
   Recording the behaviour change in [porting-notes.md](porting-notes.md) is owned by
   `CLAUDE.md:156-157` — follow it there, rather than reading a second version of it here.

## Where every number lives

"Never invent a number" is only followable if every kind of number has an address. These are the
addresses.

| What you need | Where it is authoritative |
|---|---|
| Formulas, build costs, trait prices, growth rates, shop markup, and the shape of the levelling curve | [gameplay.md](gameplay.md) — read off the code, with Java file citations. Prose, so it can drift: the source below wins on any disagreement |
| Exact arithmetic ground truth: attack resolution, derived combat stats, creation allocations, shop pricing, quest and overload accounting, the levelling curve, monster drops | `baseline/rules.txt` — machine-generated by `./gradlew baseline`; a diff is a port defect (`docs/development.md:88-93`) |
| How the game plays over large samples: hit rate per Skill matchup, fight outcomes per monster and hero build | `baseline/distributions.txt` — checked by shape, not exactly (`docs/development.md:94-96`) |
| Static content: weapons, armour, monsters | `content/arms.json`, `content/gear.json`, `content/monsters.json`, regenerated by `./gradlew exportContent` (`docs/development.md:141-145`) |
| Where a number deliberately departs from 1997, and why | [porting-notes.md](porting-notes.md) |
| The live value the game actually uses, and the exact levelling numbers | The TypeScript source: `app/src/rules/` for the maths, `app/src/game/` for content and constants |

Two of those rows can cover the same value, so the order of authority is three deep:

1. **The TypeScript source under `app/src/`** — what the game actually does. It wins over any
   document, always.
2. **`baseline/rules.txt` and `baseline/distributions.txt`** — what the Java reference does. A
   disagreement between these and the TypeScript source is a port defect: report it, do not pick a
   side.
3. **[gameplay.md](gameplay.md) and [porting-notes.md](porting-notes.md)** — prose written from the
   code. Read them for the reasoning and the Java citations, never as the tiebreaker, because prose
   drifts and nothing here checks it.

That last point is a worked example rather than a caution. Until the change that added this
document, gameplay.md gave the third and fourth steps of the levelling curve as 113 and 169, having
rounded where the code truncates to 112 and 168 — the curve is stated at
`app/src/rules/levelling.ts:18` and computed at `app/src/rules/levelling.ts:22-24`. It had been
wrong for the life of the file and nothing caught it, because no test reads a document. The line is
now right; the ordering above is what stops the next one mattering.

## What to push back on

Push back means say so and propose the alternative. It does not mean refuse and stop.

- **Anything needing a server or other players.** There is none, and the features that assumed one
  are gone rather than dormant (`docs/porting-notes.md:42-58`).
- **Anything that reintroduces daily pacing, gear decay or a harsh death penalty.** All three were
  removed on purpose, and the reasoning is on the page (`docs/porting-notes.md:22-27`).
- **Anything framed as an ending, a win condition or a final boss.** The game is endless and the
  player stops when they want; see [design-vision.md](design-vision.md).
- **A change that breaks a stated intent without saying which one and why.** Breaking one is
  allowed. Doing it without naming it is not.
- **A request that supplies no number and no source for one.** Ask where the number comes from
  before you write it, and take the answer from the table above.

## What this document does not own

- **Regenerating the baseline, and the commit note that says what moved** — `CLAUDE.md:150-155`,
  with the reasoning at `docs/roadmap.md:14-35`. This document only fixes where it sits in the
  order.
- **Recording a behaviour change in porting-notes.md** — `CLAUDE.md:156-157`.
- **The design intent itself** — [design-vision.md](design-vision.md). This document is the
  procedure; that one is the substance every step of it refers back to.
